# Q1: Rust 为什么默认不可变？ ✅

欢迎来到 Rust 设计的第一个灵魂拷问：为什么变量默认就是不可变的？🦀 在其他很多语言里，变量默认可变似乎是「天经地义」的事，但 Rust 却反其道而行之。这个选择并不是为了刁难开发者，而是 Rust 安全哲学的核心体现。

## 🧭 引入与类比

想象你正在读一本推理小说，如果书中的关键线索在中途被悄悄改掉，你会不会抓狂？代码也是如此。**默认不可变**就像给数据贴了一张封条：一旦绑定，除非你明确撕开它，否则它不会被改变。这样读代码的人可以放心大胆地推理，不用时刻担心某个值在别处被偷偷修改。

## 💡 核心概念图解

Rust 的不可变性由编译器在编译期保证：

```
let x = 5;      // ✅ 编译器：x 是只读的
x = 6;          // ❌ 编译错误：cannot assign twice to immutable variable
let mut y = 5;  // ✅ 显式声明 y 可变
y = 6;          // ✅ 可以修改
```

## 🔧 深入讲解

默认不可变带来三大好处：

1. **可读性提升** 👀：看到 `let x = 5;` 你就知道，无论后续代码多长，`x` 始终是 5（除非被 shadow）。
2. **并发安全** 🧵：不可变数据可以安全地在多个线程间共享，不会出现数据竞争。这是 Rust  fearless concurrency 的基础。
3. **优化机会** 🚀：编译器可以更激进地优化不可变数据，比如缓存值、消除冗余读取等。

当确实需要修改时，Rust 要求你显式写上 `mut`：

```rust
let mut count = 0;
count += 1;
```

这个小小的 `mut` 就像交通信号灯 🚦，让代码中的所有「变化点」一目了然。

## ⚠️ 常见误区

- **误区 1**：不可变等于常量。
  - ✅ 正解：`const` 是编译期常量，必须标注类型且不能依赖运行时值；`let` 绑定的是运行期变量，可以被 shadow。
- **误区 2**：`mut` 会影响性能。
  - ✅ 正解：`mut` 只是向编译器和读者声明意图，不会带来运行时开销。
- **误区 3**：内部可变性（如 `RefCell`）违反了不可变规则。
  - ✅ 正解：不可变只是对编译期借用规则的保证，运行时检查的内部可变性是 Rust 允许的另一种模式。

## 📝 一句话总结

Rust 默认不可变，是为了让代码更安全、更可读、更适合并发；当你真的需要改变时，`mut` 会帮你把变化点标记得清清楚楚。
